## Overview

База туров бота (`tours_text`, читается каждым ответом LLM) сейчас обновляется только вручную с деплоем и рестартом. Нужна автоматическая синхронизация из папки Google Drive: фоновая проверка раз в 5 минут, пересборка базы в памяти без рестарта. Ответы клиентам по-прежнему идут из памяти — в Google на каждое сообщение никто не лазит.

Контекст и проверенные факты — в плане `C:\Users\AUTHOR\.local\share\opencode\plans\tour-sync-plan.md` (публичность папки, анонимный экспорт, невозможность статического перечисления).

## User Roles

- **Владелец**: правит документы в папке Drive, ожидает появления изменений в ответах бота без деплоя.
- **Менеджер**: получает в Telegram уведомления об изменениях цен/дат/ссылок и о проблемах синхронизации.

## Requirements

### FR-1: Периодический опрос папки

**User Story:** As владелец, I want бот сам проверяет папку раз в 5 минут, so that правки в документах доходят до клиентов без моего участия и деплоя.

**Acceptance Criteria:**
1. WHEN воркер тикает по интервалу THEN система SHALL опросить Drive API (`files.list` по ID папки).
2. WHEN опрос успешен AND ничего не изменилось THEN система SHALL ничего не делать (ни перезаписи, ни логов выше debug).
3. WHEN sync отключён или не настроен THEN система SHALL спать и работать по старой схеме (DOCX при старте).

**Edge Cases:**
- Сеть недоступна → пропуск тика, last-good живёт, процесс не падает.

### FR-2: Скачивание только изменившегося

**User Story:** As владелец, I want синхронизация не дёргает Google зря, so that не упираемся в квоты и не шумим.

**Acceptance Criteria:**
1. WHEN у документа `modifiedTime` не изменился с прошлого тика THEN система SHALL не скачивать его заново.
2. WHEN документ новый AND тип — нативный Google Docs THEN система SHALL скачать его экспортом (`export?mimeType=text/plain`).
3. WHEN документ новый AND тип — загруженный `.docx` THEN система SHALL скачать тело файла и разобрать абзацы (оба типа проверены живьём в папке: 4 нативных + 2 загруженных).
4. IF тип другой THEN система SHALL пропустить файл.

### FR-3: Сборка через существующий разбор

**User Story:** As владелец, I want в памяти тот же формат базы, что сейчас, so that поведение бота не меняется.

**Acceptance Criteria:**
1. WHEN документ собран THEN система SHALL применить ту же обработку, что `tour_loader`: заголовки/ссылки, нормализация виз (3 состояния), фильтр прошедших и распроданных дат, лимит ближайших дат.
2. WHEN в Google-документе нет ссылки на бронирование THEN система SHALL исключить документ из базы и отметить его для уведомления (а не молча класть в общие заметки).
3. WHEN ссылка на бронирование известна из прошлого состояния THEN система SHALL перенести её на новую версию того же документа (узнаём по ID документа, а не по названию).
4. WHEN идёт первый запуск THEN система SHALL подхватить брони из текущей базы: по каноническому имени (регистр/расширение/пробелы/тире игнорируются), а для расходящихся имён — по явным алиасам `TOUR_SYNC_NAME_ALIASES` («Эльбрус 2027» = «Горнолыжный отдых на Эльбрусе», «Варшава-Дрезден-Прага» = «ВДП»).
5. WHEN имя документа содержит мусор («Двойные  пробелы», «.docx» в названии) THEN система SHALL очистить его для заголовка секции, смысл и регистр не трогаем.
6. WHEN у документа есть ссылка на тур THEN система SHALL использовать фактический URL документа, из которого он собран.

### FR-4: Валидация перед публикацией

**User Story:** As владелец, I want битая выдача никогда не попадала в базу, so that один сбой сети не оставляет бота без туров.

**Acceptance Criteria:**
1. WHEN результат пустой (0 туров) THEN система SHALL не публиковать его никогда.
2. WHEN туров меньше порога `tour_sync_min_tours` THEN система SHALL не публиковать и уведомить.
3. WHEN число туров упало более чем вдвое относительно текущей базы THEN система SHALL не публиковать и уведомить.
4. WHEN все проверки пройдены THEN система SHALL опубликовать результат.

### FR-5: Публикация только по изменению

**User Story:** As владелец, I want кэш DeepSeek не инвалидируется зря, so that не растёт счёт за входные токены.

**Acceptance Criteria:**
1. WHEN хэш новой сборки совпал с текущей базой THEN система SHALL не подменять текст.
2. WHEN хэш отличается AND валидация пройдена THEN система SHALL атомарно подменить текст в памяти и сохранить снапшот на диск.
3. WHEN публикация произошла THEN система SHALL залогировать `tours.ready`-стилем (туры/знаки) и уведомить об изменениях цен/дат/ссылок и состава.
4. WHEN это первая публикация THEN система SHALL сверить состав с текущей базой (алиас-чувствительно) и явно указать в уведомлении туры, которых нет в папке, — их исчезновение не должно проходить молча. Порог просадки применяется и к первому запуску (счёт — от числа туров в базе).

### FR-6: Fallback-цепочка

**User Story:** As владелец, I want бот отвечает даже если Google лежит при старте, so that клиенты не страдают от чужих сбоев.

**Acceptance Criteria:**
1. WHEN старт AND Drive доступен THEN система SHALL собрать базу из Drive.
2. WHEN старт AND Drive недоступен AND есть снапшот THEN система SHALL загрузить снапшот.
3. WHEN нет ни Drive, ни снапшота THEN система SHALL загрузить локальные `tours/*.docx` как раньше.

### FR-7: Уведомления

**User Story:** As менеджер, I want знать об изменениях туров и сбоях, so that не узнаю о проблемах от клиентов.

**Acceptance Criteria:**
1. WHEN изменились цена/даты/ссылки/состав THEN система SHALL отправить уведомление в Telegram (если `tour_sync_notify` включён).
2. WHEN синхронизация падает N тиков подряд THEN система SHALL отправить уведомление об ошибке (без спама на каждый тик).
3. WHEN Drive вернул 4xx (ключ/доступ) THEN система SHALL уведомить сразу — само не починится.

## Non-Functional Requirements

- **Безопасность:** доступ к Drive — файл сервисного аккаунта (приоритет) или API-ключ; всё только в `.env`/файлах сервера. Ключ, токен и URL с секретами никогда не попадают в логи, коммиты и Telegram. JSON-ключ сервисного аккаунта в репозиторий не кладётся (`.gitignore: credentials/`).
- **Надёжность:** любое исключение внутри воркера ловится, процесс живёт дальше.
- **Производительность:** на каждое сообщение клиента — ноль обращений к Google (только память).
- **Совместимость:** формат итогового текста идентичен текущему `load_tours()` — `prompts.py` не трогаем.

## Out of Scope

- Автоподбор списка через что-то кроме Drive API (браузерный скрапинг — нет).
- Правки самих Google-документов из бота (только чтение).
- Изменение промпта и правил ответов (формат базы не меняется).
- Перезапись локальных `tours/*.docx` из синхронизации (они остаются fallback-источником).
