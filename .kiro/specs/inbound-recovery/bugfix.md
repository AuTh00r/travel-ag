# Раннее срабатывание таймера Windows — 2026-10-20

Уточнение существующего контракта FR-12/13, AC-27..30 и решения 0012;
до реализации. Локальная правка меньше одного дня, без изменения архитектуры.

Current: `scan_call` и самостоятельный `sync_dialog` определяют владельца
TimeoutError сравнением `time.monotonic()` с deadline. На Windows Python3.12.10
monotonic имеет resolution15.625мс; собственный таймер может сработать до этого
сравнения. Изолированная проверка действующего `reconcile_tick` без API/БД:
21 ложная ошибка и backoff из30 запусков, cursor сохранён. В production за
19–20 октября90 событий с такой сигнатурой; принадлежность каждого исторического
события этой причине без дополнительных метаданных отдельно не доказана.

Expected: при срабатывании собственного таймера считать deadline штатной
границей независимо от повторного чтения часов. Внутренний ранний TimeoutError
остаётся ошибкой с backoff; внешняя отмена распространяется. Для позднего
внутреннего исключения сохранить прежнюю проверку уже исчерпанного deadline.
Оба пути сохраняют unread cursor и корректно завершают отменённый await.

Unchanged: интервалы60/120/480/5с, API15с и бюджет90с/100 GET, scope allowlist,
первый baseline, дедупликация/receipts/unknown, отмена по менеджеру, схемы БД.
В исходную локальную правку production, Git stage/commit/push и очистка данных
не входили. Затем20Oct владелец отдельно ответил «+» на готовый фикс:
выкладка без изменения scope выполнена, факты в rollout.md.

Проверки: детерминированный early callback настоящего asyncio timer для общего
обхода, priority dialog и самостоятельной свежей проверки; внутренний ранний
timeout, внешняя отмена, успешный запрос и cursor после рестарта. Затем профильный
pytest, полный pytest, Ruff, diff и read-only review. Модель/Graph/доставка — заглушки.

# Отмена по менеджеру перед восстановлением — 2026-10-18

Микро-исправление, одобрено «+» после разбора логов; до кода.
Current: process сначала вызывает can_resume; при gap расходует два повтора,
даже если manager_last_at уже активен. На последней попытке final_failure
создаёт context, get_session отвергает активного менеджера, внешний StaleWork
превращается в failed_final/session_or_source_changed вместо cancelled.
Evidence: read-only production 19:45 Minsk: fresh_context_unavailable дважды,
manager_active=True, source version 1/1, failed_final, notifications=0.

Expected: под client lock до свежего API-контекста проверять актуальность
задачи и manager pause/pending; повторять проверку сразу после await refresh,
включая False/исключение. При перехвате отменять только текущую processing
задачу с действующим claim, без модели, повторов и новых уведомлений.
Внешний StaleWork также должен отменять задачу при активном менеджере,
а не записывать технический отказ. Снятие паузы не возрождает cancelled.

Unchanged: scope/claims/source revisions, 120/480 technical delays для реальных
сбоев без менеджера, receipts/unknown, final fallback при исчерпании повторов,
сессия и лимиты, ранее завершённые задачи, локальная пагинация TSK-021.
Не отменять newer owner и не переводить unknown/delivering в processing.

Проверки: активная пауза до process на initial/recovered/последней попытке;
пауза или pending появляется во время refresh=False; StaleWork после refresh;
снятие паузы; контроль реального gap без менеджера. Настоящая временная SQLite,
API/модель/отправки — заглушки. Полный pytest/Ruff/review/diff. Без production.
