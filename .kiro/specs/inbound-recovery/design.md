# Восстановление входящих: Design

## Micro 2026-11-04: окно тишины

Legacy: при новом сообщении в ещё собираемый пакет отменить только текущий
ожидающий task и зарегистрировать новый без await между заменами. Прежний
finally проверяет владельца; map очищается до AI, поэтому AI не отменяется.
Recovery: первый непрерывный prefix по received_at,rowid, gap<=5с;
готовность last_received+5<=now. Gap>5с оставляет следующий пакет отдельно,
даже если tick запоздал. Persisted received_at прежний, MID-retry его не
меняет. Новых схем/флагов и дедупликации текста нет.

## Выкладка проверки участников — 2026-11-01

Минимальный выпуск меняет только `src/services/inbound_recovery.py` и SHA этого
файла в runtime manifest. Новых настроек, схемы SQLite и правил маршрутизации
нет. Применяется существующий guarded source rollout: проверка прежних SHA,
backup исходника/manifest/SQLite, проверка отсутствия активной доставки и чужих
Python-процессов, атомарная замена и штатная задача RestartTravelBot. Откат
кода не восстанавливает рабочую SQLite. После запуска сверяются все runtime SHA,
health, прежний allowlist/1, временные границы и подтверждённые/неопределённые
отправки. Отсутствующий участник реального Meta-диалога остаётся явным gap.

## Единство времени story hint — 2026-10-20, до кода

`InboundStore.story_hint` нормализует аргумент before существующим timestamp()
в UTC-seconds до запроса SQLite. None/nonfinite дают отсутствие hint, не now().
Payload и MID не переписываются; порядок потребления прежний. По указанию
владельца окно увеличено до600с в legacy cache и default story_hint (20Oct).
Parser логирует story reaction как received с context_usable; recovery merger
логирует attached при выборе exact ID. Источник дополняет ближайший plain вопрос,
затем используется прежний story resolver/image-or-video/model handler.

## Уточнение штатного deadline на Windows — 2026-10-20

В `scan_call` и owned `sync_dialog` собственный таймер определяется через
`asyncio.timeout(...).expired()`, а не только сравнением часов после исключения.
Это сохраняет решение0012: общий deadline — штатная граница с сохранённым cursor.
Если собственный таймер не сработал, ранний внутренний TimeoutError остаётся
ошибкой; для уже истёкшего deadline сохраняется прежний выход по бюджету.
Внешняя CancelledError не перехватывается. Допуски времени, новые настройки,
повторы, фоновые задачи и изменение schema не добавляются. Python3.12 поддержан.

## Дополнительные отказы business pipeline — 2026-10-18

TSK-024 использует fixture настоящего main dispatch с подменой внешнего
ainvoke/send. После частичной/unknown доставки создаются новые store/service
с той же SQLite; свежесть проверяет настоящий refresh_client/sync_dialog
через Graph-заглушку. Перехват менеджером синхронизируется asyncio.Event
внутри ainvoke; manager-event сохраняется до освобождения ответа модели.
Новых runtime-компонентов, состояний и архитектурных решений нет.

## Приёмочный стенд — 2026-10-18

TSK-023 использует прежний RecoveryService, новый экземпляр InboundStore на
той же временной SQLite и настоящий main._dispatch_user_event. Заглушки
только на границах Graph/LLM/Instagram/Telegram; refresh_client/sync_dialog,
claim/startup/commit/delivery не подменяются. Синтетический MID из API не
проходит webhook до подтверждённой отправки. После второго restart тот же
MID приходит из API и webhook: одна задача, один ответ/receipt и одна пара
user/assistant в истории. Отдельный вариант теряет claim до модели: истекает
lease, startup сохраняет retry 120 с. Изменений архитектуры и runtime нет.

## Приоритет менеджера — микро-исправление 2026-10-18

См. bugfix.md (до кода). Синхронный _processing_stopped сначала проверяет
текущий processing state и claim, затем session pause/pending; finish использует
прежний assert_claim. Helper вызывается под client lock до и после can_resume,
а также перед technical retry во внешнем StaleWork catch. Уже изменившийся
владелец/состояние останавливает старый worker без записи. Новых данных,
настроек, маршрутов доставки и архитектурного выбора нет.

## Постраничное покрытие диалога — 2026-10-18, до кода

Решение: `.kiro/decisions/0013-resumable-message-coverage.md` (6/6, accepted).
Локальная реализация и QA завершены: TSK-021, 1454 PASS. Совместный выпуск
1480 PASS выложен по отдельному «деплой»: PID4136/29 SHA, реальный after PASS,
gap=false, scope allowlist/1 сохранён. См. rollout.md.

В существующий JSON checkpoint `dialog:<client>` добавляется необязательное
`pending`: ID диалога, целевой through, верх продолжаемого окна, after,
признак недостоверных записей и ограниченные digest ранее посещённых cursors.
Новых таблиц/флагов нет. Старый checkpoint читается без преобразования.
`checked_at` отражает чтение свежей головы, не завершение старой страницы.

Каждый вызов сначала сохраняет всю свежую страницу. Если голова уже достигла
старой границы и записи достоверны, gap закрывается. Иначе используется
сохранённый after старого окна либо after новой головы. Сначала события,
затем continuation; падение между ними даёт безопасный повтор MID. По
достижении строгой временной границы или конца through продвигается только
на подтверждённый верх окна. Свежая голова может расширить верх лишь при
доказанном соединении со старым окном; иначе требуется ещё одно окно до
нового through. Недостоверные поля оставляют gap, даже если cursor закончился.

API adapter принимает optional after для того же проверенного Graph path;
Authorization остаётся header-only. Нормализатор обрабатывает полный data,
покрытие проверяет представимость каждого MID, а не равенство числа events
числу rows. Повтор cursor останавливает проход; invalid message cursor
сбрасывает только pending этого диалога, сохраняет through и общий discovery.

Новый per-client sync lock отделён от processing/delivery `client_locks`,
чтобы refresh под уже удерживаемым delivery lock не зациклился. Бюджет
сканера наследуется; независимый refresh создаёт свой ограниченный контекст
с прежним pacing и deadline. Исчерпание возвращает неполноту direct refresh,
а scanner сохраняет свою штатную границу бюджета. Новая голова может отменить
задачу по ответу менеджера ещё до завершения старого хвоста.

При бюджете одного GET свежая голова расходует его целиком, поэтому хвост
не продвигается; для продвижения нужны минимум два GET и достаточный
deadline. Штатный лимит — 100; конфигурация в этой доработке не меняется.

## Исправление планирования сверки — 2026-10-18, до кода

В одном `reconcile_tick` приоритетные сохранённые checkpoint `dialog:<client>`
из текущего allowlist проверяются перед общим обходом. Допускаются только
checkpoint с совпадающим client_id и непустым строковым ID. Порядок — oldest
checked_at first; итог чтения используется повторно, если общий обход встретит
тот же диалог. All scope оставляет общий обход; существующие baseline не меняются.

Ограничение запросов привязано к фактическому входу в сетевой метод в `_get`,
после общего rate limiter. Контекст бюджета ограничен задачей сканера через
ContextVar, чтобы одновременный refresh перед доставкой работал независимо.
Исчерпание бюджета — штатное завершение тика без ошибок/backoff; непрочитанный
элемент cursor сохраняется. Исчерпание deadline — та же штатная граница,
чтобы большой общий обход не наращивал ложный backoff 30/120/300; ранний
сетевой timeout и auth/rate-limit сохраняют прежний путь ошибок.
Новых таблиц, настроек и фоновых служб нет. См. FR-12/13, AC-27..30.
Решение: `.kiro/decisions/0012-priority-recovery-scan.md` (review 6/6, accepted).

Статус: Design утверждён пользователем 2026-10-15 с изменением интервалов
строки «Проверка обработки» ×4. Requirements утверждены 2026-10-15.
Локальная реализация завершена 2026-10-16; текущая версия выложена для теста
только @_shelter_0. Остальные клиенты сохраняют прежний маршрут.
Первый candidate остаётся HOLD. Общий parser/merge проверен; 2026-10-16
разрешена новая тестовая сборка и включение только @_shelter_0 с известными
ограничениями API-only voice/post. Независимый приёмник исключён пользователем.
Интеграционное решение: `.kiro/decisions/0006-inbound-processing-drafts.md`.

### Уточнение интеграции 2026-10-16

Переиспользуется единый валидатор `reply/manager`, без второго JSON-формата.
Неполный API-only контекст разрешает молчание отдельным processing-флагом,
а не фиктивным ADS referral. ContextVar ограничивает staging одним клиентом:
session-записи, уведомления и ответы становятся draft, а не фиктивным успехом.
Уведомление возвращает явный deferred receipt; счётчик и история assistant
меняются только после настоящего подтверждения. Финализация использует прежние
правила контактов и `_finalize_handoff_reply` после фактического Telegram outcome.
Немедленный format retry внутри обработки (до двух LLM вызовов) сохраняется;
два durable повтора относятся к завершившейся технической ошибке обработки.
Обязательные human-only исходы не получают semantic recheck.

Read-only проверка production 2026-10-16: четыре GET, три диалога, десять
текстовых сообщений, все HTTP 200. Вложений в выборке нет. Старый log
`instagram.message.received` не содержит MID, поэтому равенство API/webhook
по нему проверить нельзя. Последующая read-only проверка тестового диалога
сопоставила API ID с `mid` двух событий `instagram.non_text.received` и
`instagram.referral.received` от 2026-10-11; evidence в runtime note.
Свежие образцы подтвердили image_data.url и video_data.url: фото доступно,
два видео полностью прочитаны в память. Конкретные голосовое и ig_post
вернулись is_unsupported=true, вложения не появились и через отдельный edge.
Reels вернул shares.data[].link; выявленная граница API-нормализатора закрыта
доработкой первого выпуска. Read-only lookup permalink подтвердил точную
VIDEO-публикацию, media_url и caption. Полный live delivery/manager gate ещё
не пройден. Разрешено только тестовое включение для его проверки.

### Первый выпуск: scope и проверенные медиа — 2026-10-16

### Уточнение parity после замечания пользователя

Решение `.kiro/decisions/0008-inbound-shared-parser.md`: API адаптирует только
подтверждённые поля в форму обычного сообщения; classification выполняет
тот же parse_message_payload, что receive_message. Отдельная API-classification
убрана. Общая mixed-media группировка работает независимо от источника.
Поздний webhook может вернуть API-only ignored событие в обработку, но не
старше baseline; переклассификация в GIF/story_context закрывает неподтверждённую
задачу без вызова модели. Story reaction расходуется ровно первым следующим
сообщением, snapshot сохраняется при одинаковом позднем вопросе.
43 parity-сценария; полный regression 1283 PASS. Это не доказательство
получения содержимого, отсутствующего в Meta API.

Независимый приёмник обсуждался и отклонён пользователем 2026-10-16.
В этом выпуске остаются существующий webhook, SQLite и самостоятельная сверка
Conversations API. Получение исходника для двух проверенных unsupported-событий
не решено; fallback менеджеру не считается успешным восстановлением медиа.

Принятое решение: `.kiro/decisions/0007-inbound-recovery-canary.md`, review 6/6.

Один scope из `INBOUND_RECOVERY_SCOPE=allowlist|all` (default allowlist) и
`INBOUND_RECOVERY_CLIENT_IDS` (CSV числовых IDs). Enabled с пустым/невалидным
allowlist не запускается. Scope применяется к выборкам SQLite и перед send,
для Telegram — job.client_id. Mixed webhook делится до parser side effects;
recovery persist предшествует legacy dispatch. Неохваченные pending остаются
legacy; связанные receipts не переводятся в слепую отправку.
Activation metadata в inbound_sync: baseline клиента для canary; первый all
baseline отдельно. Effective baseline — сохранённая client baseline, иначе
all baseline. Смена scope сбрасывает только scan cursor/completion; job/MID/
receipts и отмены менеджером сохраняются. Scanner читает messages только
включённых клиентов, показывает собственную область покрытия.
Подтверждённые share permalink передаются shared resolver; mixed parts идут
через существующий composite media flow. Недоступное API-содержимое остаётся
incomplete с явной причиной; единый LLM JSON не меняется.

| Решение | Предлагаемое поведение |
| --- | --- |
| Приём и перезапуск | Сохранять входящее до ACK; восстанавливать незавершённое из SQLite |
| Проверка обработки | Каждые 60 с; до двух технических повторов через 120/480 с |
| Пропущенные уведомления | API после запуска и каждые 120 с; полный обход может занять больше одного тика |
| Молчаливый модельный handoff | Один пересмотр через 120 с, без дубля доставленных уведомлений |
| Менеджер и дубли | Проверять постоянные receipts/паузы; неизвестную доставку не повторять вслепую |
| Ограничения Meta | Детали только 20 последних сообщений; полный ad/story/media-контекст не доказан |
| Очистка нового журнала | Payload завершённых задач — 7 суток, служебные MID/receipts — 90; незавершённые не удалять; прежнюю историю не очищать |
| Включение | По умолчанию выключено; production-проверка и rollout отдельно |

## Поток данных и границы изменений

Webhook и API используют общий `persist_events`; затем существующий
`InstagramChannel.merge_events` формирует задачи. Восстановление выполняет
те же бизнес-правила и использует ту же модель, медиаподготовку и контакты.
Новый worker не определяет понятность запроса списком туров.

| Область | Изменение |
| --- | --- |
| `src/db/inbound.py` — новый модуль | Схема, транзакции, аренды, дедупликация, исходы и контрольные точки |
| `src/services/inbound_recovery.py` — новый модуль | Типы ProcessingContext/ProcessingResult, планирование, сверка, повторы и доставка |
| `src/channels/instagram.py` | Read-only методы Conversations API, ограниченный нормализованный результат; структурированный исход отправки |
| `src/main.py` | Подключение worker в lifespan, приём до ACK, явные результаты всех ветвей dispatch, проверки перехвата |
| `src/db/sessions.py` | Версия сессии и транзакционная запись результата без изменения публичной формы истории |
| `src/db/pending_messages.py` | Совместимая связь с новой доставкой; прежние записи сохраняются |
| `src/services/telegram_notify.py` | Подтверждения по каждому получателю, использование прежнего форматирования |
| `src/config.py`, `.env.example` | Отключённые по умолчанию флаги и интервалы |
| `src/ai/prompts.py` | Ограниченное указание на восстановленный неполный контекст, без выдуманного ad_id |

Сервисы не импортируют `main`; dispatch и существующие отправители передаются
как callbacks. Срезание других частей main, новые серверы, Redis и новые
permissions Meta в объём не входят.

## Постоянная модель данных

Новые таблицы находятся в том же `data/sessions.db`. Для записи используется
одно соединение, короткие транзакции, WAL и существующий timeout.
Сеть, модель и декодирование не выполняются внутри транзакции.

| Сущность | Ключевые данные и инварианты |
| --- | --- |
| `inbound_events` | `mid` уникален в пределах подключённого IG-аккаунта; клиент/диалог, исходное время, время приёма, нормализованное событие, источники API/webhook, полнота/версия контекста, текущая задача-владелец |
| `inbound_jobs` | ID, клиент, неизменяемый набор MID, состояние/причина, snapshot контекста, validated result, следующий запуск, технические попытки, использованный semantic recheck, claim token/lease, superseded_by |
| `inbound_deliveries` | Задача, канал Instagram/Telegram, назначение, часть, payload, `ready/sending/retry_wait/sent/unknown/blocked/cancelled`, время intent, подтверждённый внешний MID; уникальность логической части/назначения |
| `inbound_sync` | Постоянная граница включения, незавершённый проход списка диалогов, курсор и ошибки; отдельно полнота/последняя успешная сверка каждого диалога |
| `sessions.revision` | Монотонная версия сессии для compare-and-set; существующий JSON и клиентские данные сохраняются |
| `pending_messages.recovery_delivery_id` | Nullable UNIQUE-ссылка; прежние строки без ссылки остаются валидными |

MID — идентичность сообщения; задача — результат одного merge; результат
доставки относится к явному набору MID. Наличие события или последнего
assistant в истории не означает успешную обработку этого набора.
В текущем протоколе enrichment пересобирает того же owner с прежним ID,
а не переносит MID в другую задачу. Cross-job supersede не используется;
вместо отдельного superseded_by доказательство покрытия хранится в members
и явном результате legacy_covered для подтверждённого legacy dispatch.

API дополняет известное событие, но не стирает более богатые webhook-поля.
Поздний webhook может обогатить API-событие, не создавая вторую задачу.
Материальное изменение источника/вложения меняет версию snapshot: устаревший
результат нельзя отправить без повторной проверки. Если отправка ещё не
началась, план пересобирается в пределах общего бюджета попыток; если часть
уже отправлена или её исход неизвестен — проверка оператором, без второго
автоматического ответа на тот же MID.

## Приём webhook и группировка — FR-1, FR-2, FR-6

1. Сохранить прежние signature/JSON-проверки и нормализацию канала.
2. Одной транзакцией записать все новые нормализованные события запроса;
   уникальность MID обеспечивает durable-дедупликацию. При ошибке записи
   вернуть 503, не резервировать MID только в памяти и не отвечать 200.
3. Только после commit подтвердить приём. In-memory MID-кэш — ускорение,
   а не источник истины; parser не должен скрыть ещё не сохранённое событие.
4. Ждать пять секунд тишины (уточнение04Nov); соседние новые сообщения
   продлевают окно. received_at и нераспределённые события восстанавливаются
   из БД; gap>5с разделяет пакеты. MID игнорируемых
   событий тоже получают явный итог; story-context сохраняется с прежним TTL.
5. После merge атомарно назначить события задачам; ошибка одной задачи
   не уничтожает остальные события пакета. Разные объявления и обязательные
   человеческие события не склеиваются новым механизмом.

Между обработкой одного клиента сохраняются прежние locks. Менеджерский
сигнал имеет приоритет и постоянно отменяет ожидающие задачи. Критический
сигнал `_manager_pending` выставляется до фоновой медленной работы; если
сохранение webhook не удалось, сигнал не превращается в фиктивную вечную паузу.

До классификации echo как manager канал проверяет постоянные own-MID receipts,
а не только текущие `_sent_mids/app_id/_pending_sends`. Подтверждённое собственное
эхо после рестарта не создаёт takeover. Раннее эхо при незавершённом send intent
сохраняется как receipt metadata/неопределённое авторство, а не теряется из-за
раннего `continue`. Слабое совпадение текста не подтверждает доставку и не
доказывает менеджера; прежняя защита от ложного early-echo takeover сохраняется.

## Выполнение, история и атомарность — FR-2, FR-3, FR-5

`ProcessingContext`: job/claim, исходные MID и время, версия сессии и источника,
тип запуска, технический/семантический счётчики, полнота контекста.
`ProcessingResult`: подготовленный ответ/уведомление либо явный исход
`silent_model_handoff`, `technical_retry`, `human_only`, `manager_cancelled`,
`ignored`, `failed_final`. Ветки guard, rate limit, ошибок media/STT/LLM
и ранние return также обязаны иметь результат; None не считается успехом.

`claim_due_job` атомарно выдаёт уникальный токен и lease на 180 с. Heartbeat
каждые 15 с продлевает аренду во время медиа/STT/LLM. В одном процессе живой
зарегистрированный task не запускается повторно только из-за задержки тика.
После перезапуска незавершённая задача подхватывается с новым токеном;
устаревший токен не может сохранить результат или начать внешнюю отправку.
Сохраняется текущий режим одного Uvicorn worker; multi-worker не вводится.

Все ветви в recovery-режиме возвращают план, а не самостоятельно делают
несогласованные save_session/send/notify. Подготовка результата завершается
одной транзакцией: проверить claim, revision, контекст и менеджерскую паузу;
сохранить validated result, изменения истории, планы и итог задачи.
Если ответ зависит от передачи менеджеру, это пока draft с блокировкой
на notification outcome; готовая клиентская доставка и legacy-проекция
появляются только после финализации фактического результата уведомления.
`get_session/save_session`, открывающие отдельные соединения, внутри этой
транзакции не вызываются. Конфликт версии не перетирает более свежую сессию.
Все писатели sessions, включая manager/admin reset и обычный save_session,
сохраняют и увеличивают revision. Старый INSERT OR REPLACE не должен сбрасывать
её к default; наружная форма get_session при этом не меняется.

История получает внутренние связи с исходными MID/частями доставки. Перед
моделью передаются только прежние role/content. Повтор и пересмотр не добавляют
пользователя второй раз; уже записанные реплики текущего набора не подаются
одновременно как история и повторный текущий вопрос. Проекция строится без
изменения сохранённой истории. Assistant фиксируется вместе с подтверждением
его части доставки, а не по факту генерации.

Новая реплика не закрывает старую задачу автоматически. Неподтверждённый
старый вопрос можно включить в новую задачу лишь явно, с его контекстом и MID,
без конфликта источников; переход superseded и смена владельца атомарны.
Доставленный результат новой задачи покрывает только включённый набор.
Одна временная отметка последнего ответа не используется как доказательство.
Это учёт обработки, а не отдельная нейросетевая оценка качества каждого ответа.

## Доставка и совместимость очереди — FR-7

`inbound_deliveries` хранит постоянный план/intent/receipt. Существующая
`pending_messages` остаётся очередью только безопасно повторяемых Instagram-
отправок: в неё не помещаются Telegram-уведомления, sent и unknown.
Только окончательный безопасный текст и ссылки на исходящую очередь создаются
атомарно. Незавершённый draft, особенно с неподтверждённым «передал», остаётся
только в новом журнале и недоступен legacy worker даже при откате.
Сохранённый результат модели не вызывает модель повторно даже после перезапуска.

Перед первой внешней отправкой задачи все её оставшиеся queue-проекции
атомарно снимаются с обычной очереди, фиксируется intent текущей части.
Части идут последовательно. Receipt и история фиксируются одной транзакцией.
При подтверждённом отказе, допускающем повтор, неотправленные части можно
вернуть в очередь с retry_at; подтверждённые части туда больше не попадают.
При неопределённости блокируется остаток этой задачи, а не только одна часть.

Таким образом старый worker при откате не увидит sent/unknown или Telegram
и не отправит их повторно. Незавершённый draft без готового ответа остаётся
в новом журнале; откат обязан показать оператору такие задачи, а не объявить
их доставленными. Старые queue-строки без связи доставляются без нового LLM;
включённый recovery также фиксирует их intent/receipt для авторства исходящих.
Одновременно работает один владелец доставки, не два независимых worker.

Классификация отправки:
- подтверждённый внешний message_id → sent;
- явное безопасное отклонение, например rate limit → retry_wait;
- read/write timeout, обрыв после передачи запроса, сомнительный 5xx,
  HTTP 200 без проверяемого receipt, падение при sending → unknown;
- постоянный отказ/закрытое окно ответа → blocked с наблюдаемой причиной.

Connect failure до отправки запроса можно повторять при доказуемой причине;
все transport errors не объединяются в одну автоматически повторяемую ошибку.
Результат отправки не устанавливается по совпадению текста с API-историей.
API может помочь проверить receipt, но не даёт idempotency key, делающего
внешнюю отправку и SQLite одной атомарной операцией. Exactly-once не обещается.

## Уведомления и пересмотр — FR-3, FR-4, FR-6

Уведомление готовится прежним formatter. Каждое настроенное Telegram-
назначение имеет отдельный intent/receipt в `inbound_deliveries` со стабильным
ключом заявки. Частичный успех не повторяет уже доставленные назначения.
Неопределённый ответ Telegram не повторяется вслепую; failed/limited/unknown
не считаются sent. Счётчик эскалаций увеличивается один раз после первого
подтверждённого назначения по прежней политике «хотя бы один чат».

Validated результат модели сохраняется до уведомления. После receipt
клиентский текст о передаче контакта приводится к фактическому результату
без второго вызова модели; неуспешное уведомление не выдаётся за успешное.
Повторный служебный блок использует тот же ключ заявки.

Технические ошибки, включая пойманный invalid/truncated JSON, получают
не более двух повторов через 120 и 480 с. На задачу допускается отдельно
один semantic recheck через 120 с после валидного модельного handoff.
Технический fallback не получает одновременно ещё один semantic таймер.
Счётчики общие для задачи, не обнуляются при рестарте/смене стадии;
обогащение контекста также не создаёт безлимитных вызовов.

Story mention, доказанное соавторство, файлы/товары и игнорируемые события
не попадают в semantic recheck. Самостоятельный валидный телефонный контакт
сохраняется как контакт, пустая/дублирующая template — как намеренный пропуск.

## Conversations API и неполный контекст — FR-8

Базовый подтверждённый маршрут: Graph v25.0, PAGE access token,
`PAGE_ID/conversations?platform=instagram`, participants и сообщения диалога.
Поля конфигурируются явным allowlist; `referral` не запрашивается как поле
Message. Токен передаётся в Authorization, не попадает в журнал/курсор.
Paging обрабатывается через opaque cursor и заранее известный Graph endpoint,
а не произвольный URL из ответа. Динамический signed URL не сохраняется в лог.

Сверка получает список диалогов с пагинацией, включая неизвестных клиентов.
Порядок списка/поддержка since не считаются гарантированными без проверки:
ранняя остановка по «старому» updated_time не применяется. Чтение разбивается
на сохраняемые проходы с бюджетом до 100 GET на тик, общим pacing не чаще
1 GET/с и concurrency не выше 2,
таймаутом 15 с на запрос и общим deadline тика 90 с. Первый достигнутый предел
останавливает дальнейший обход после сохранения уже полученного диапазона;
за deadline не запускаются дополнительные запросы. Свежая проверка диалога
восстанавливаемой задачи имеет приоритет над очередной фоновой страницей,
но также входит в общий бюджет. Следующий тик продолжает незавершённый проход;
полный проход может занимать несколько тиков. В БД различаются last_attempt
и complete_scan_at, сохраняются разрывы и число ещё не проверенных диалогов.

У каждого диалога хранится последняя полная граница; последующий проход
читает диапазон с перекрытием времени и durable-дедупликацией MID. Стабильное
время сервера не заменяет MID; равные timestamp сортируются детерминированно.
Курсор/граница продвигаются только вместе с сохранением найденного диапазона.
Незавершённая страница или исчерпанный бюджет не объявляются полным успехом.
При истёкшем cursor проход начинается заново, сохранённые MID не повторяются.

Документация Meta задаёт Conversations API 2 calls/s на IG Professional account;
одной concurrency недостаточно для соблюдения частоты. Scanner и адресные
recovery-проверки используют общий ограничитель 1 GET/с без burst.
Usage headers, если доступны, и прежний порог предупреждения 85% ограничивают
фоновые чтения; rate limit всегда вызывает backoff. Лимиты других интеграций
на том же аккаунте неизвестны и не объявляются зарезервированными нами.

Детали за пределами двадцати последних недоступны: старый ID сохраняется
с причиной incomplete, без выдуманного текста. Недостающие attachments/
story/referral нельзя считать пустым содержимым по умолчанию. Для API-only
запроса с неизвестным источником в модель передаётся отметка неполного
контекста; решение answer/handoff использует существующий проверяемый
JSON-контракт, не ложную метку ADS. Понятный текст можно обработать; если
для ответа нужен отсутствующий источник — молчаливая передача менеджеру.
Обычные фото/видео/голос при подтверждённых данных идут существующим маршрутом.

При API-ошибке включается backoff 30/120/300 с, при rate limit — не раньше
Retry-After; просроченный проход не запускается параллельно сам с собой.
Нормальный webhook и независимые локальные задачи продолжают работать.

## Менеджер, запуск и временные границы — FR-5, FR-8

Первое включение сохраняет baseline в UTC, не инициирует ответы более старой
переписке. Последующие запуски используют сохранённую границу, включая время
простоя. Исходное время сообщения, не время обнаружения, определяет окно ответа.
Автоматические ответы вне стандартного 24-часового окна не отправляются;
HUMAN_AGENT для автоматизации не применяется.

API-исходящие сначала сопоставляются с постоянными receipts нашего бота.
Отправитель «аккаунт компании» не идентифицирует менеджера. Сообщение вне
наших receipts и при наличии незавершённого intent имеет неопределённое
авторство: recovery блокируется для проверки, фиктивная менеджерская пауза
не записывается. Внешний ответ после baseline при полном учёте наших отправок
можно считать перехватом другим оператором/интеграцией, без угадывания личности.
Старые account-исходящие до baseline не превращают прошлые ответы бота в паузу.

Восстановленные после простоя задачи/исходящие перед отправкой требуют свежей
сверки соответствующего диалога, чтобы учесть пропущенный ответ менеджера.
Если она недоступна, эти задачи ожидают/получают явную причину, а обычные
независимые webhook-диалоги продолжают работать. Перехват отменяет ожидающие
планы; снятие паузы не возрождает отменённые задания.

Перед каждой частью доставки повторно проверяются claim, revision, snapshot,
manager_pending, постоянная пауза и актуальное окно ответа. Уже начатый HTTP
запрос нельзя атомарно отозвать при одновременном внешнем ответе менеджера;
эта гонка фиксируется как граница гарантии, не скрывается повтором.

## Очистка и наблюдаемость — NFR-1

В новых таблицах завершённые payload/draft очищаются через 7 суток;
служебные MID, receipts и причины — через 90 суток. Незавершённые/unknown/
требующие проверки задачи автоматически не удаляются. Очистка не затрагивает
существующие sessions/history и несвязанные старые pending-строки.
Само медиа повторно постоянно не копируется; необходимые временные URL
находятся только в закрытой БД и проходят прежнюю media-валидацию.

Журнал содержит локальный job ID, хэш MID, тип запуска, статус/причину,
счётчики попыток и полноту API-прохода; без текста, токенов и signed URL.
Администратору доступны counts ready/retry/unknown/incomplete, возраст
старейшей незавершённой задачи и время полной сверки. Публичный health
не раскрывает клиентов; подробности используют существующую admin-защиту.
Истечение 90-дневного dedup не возрождает старое сообщение: baseline/исходное
окно и постоянная граница сверки проверяются независимо от сохранности MID.

## Включение, проверка и откат

Предлагаемые настройки: `INBOUND_RECOVERY_ENABLED=false`,
`INSTAGRAM_RECONCILE_ENABLED=false`; интервалы watchdog=60 с, API=120 с,
lease=180 с, heartbeat=15 с. Без включения новая функция не делает API-сверок
и не меняет маршруты старого runtime. Сам rollout/включение — отдельное действие.

Перед включением нужны: проверка текущего production PAGE-токена и IG-аккаунта,
точное API ID ↔ webhook MID, реальные photo/video/audio/share/story samples
в разрешённом тестовом диалоге, проверка receipts и нового/старого queue bridge.
Получать новые scopes или менять токен ради диагностики автоматически нельзя.

Миграция только добавляет таблицы/nullable-поля/revision; существующие данные
не удаляются. Откат останавливает worker, сохраняет журнал/receipts и показывает
неоконченные draft/unknown. Он не возвращает в legacy queue подтверждённые
или неопределённые отправки и не запускает модель повторно.

Проверки реализации: AC-1..AC-21 с fake-clock, изолированной SQLite и
mock HTTP/LLM/STT/notifier. Отдельно воспроизвести падения перед/после каждого
commit и внешней отправки, устаревший claim, конкуренцию API/webhook,
частичную Telegram-доставку, исходящий old-worker при откате, неизвестного
клиента, позднее обогащение контекста и закрытое окно Meta.
Отдельные регрессии: собственное echo без app_id после рестарта не создаёт
takeover; реальный внешний ответ останавливает recovery; draft до notification
receipt недоступен legacy worker, и все session-писатели сохраняют revision.
Реальные клиентские сообщения и платные модельные тесты здесь не выполняются.
