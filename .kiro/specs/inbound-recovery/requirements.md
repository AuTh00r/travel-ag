изменение приёма событий; новую инфраструктуру без согласования не включать.

Пользователь утвердил реализацию первого включения только для `_shelter_0`.
FR-9: режим `allowlist|all`, явные числовые client IDs; enabled allowlist без
корректных IDs запрещён. Один scope ограничивает ingress, scanner, claims,
recovery/legacy pending и финальные Instagram/Telegram send по client_id задачи.
Другие клиенты сохраняют прежний маршрут. Mixed webhook сначала сохраняет
recovery-часть; при ошибке 503 до запуска legacy-части. Тестовая baseline и
первое включение all независимы; история остальных за время canary не replay.
FR-10: проверенные `shares.data[].link` проходят прежний shared resolver с
проверкой HTTPS Instagram permalink; порядок mixed media сохраняется.
API `is_unsupported` и причина неполноты сохраняются; доступный контекст
поступает прежнему reply/manager, без выдуманного ADS или содержимого.
AC-22..26: mixed webhook/storage failure без дубля; scope на всех этапах и
обычная очередь других клиентов; T1/T2 baseline + restart; Reels/mixed media;
unsupported с доступным текстом и без него. Реальные sends/LLM в автотестах
запрещены. Подготовка пакета/backup/rollback локальная; production выкладка,
enable и снятие только тестовой паузы — после отдельных разрешений.

Как владелец бота, хочу, чтобы принятый запрос не терялся при ошибке или
перезапуске и бот повторно оценивал молчаливые передачи менеджеру, пока менеджер
ещё не ответил. Понятный запрос должен получить ответ; непонятный — остаться
у менеджера без повторных одинаковых уведомлений.

Подтверждение пользователя: «Также пересматривать молчаливые передачи менеджеру».
Утверждённые параметры первого выпуска: проверка очереди каждые 60 секунд;
до двух повторов технически оборвавшейся обработки с задержками 120 и 480 секунд;
один повторный разбор молчаливой передачи через 120 секунд.
Это разные счётчики: уже выполненный разбор не повторяется бесконечно.
Уточнение 2026-10-15: множитель четыре применён только к проверке обработки
и двум техническим задержкам. Интервалы API-сверки и semantic recheck остаются
120 секунд; heartbeat, lease и API backoff не изменены.
После обсуждения утверждён гибрид: webhook + постоянная очередь + сверка
Conversations API после запуска и каждые 120 секунд. Перед реализацией
необходимо проверить чтение нашим токеном; изменение прав доступа в это
одобрение не входит.
Архитектурная основа: `.kiro/decisions/0001-inbound-recovery-hybrid.md`.

## Подтверждённое текущее поведение

- `src/main.py`, `receive_instagram_message`: MID и события сохраняются только
  в памяти, затем webhook отвечает HTTP 200 до завершения обработки.
- `_process_inbound_batch`: пакет удаляется из памяти до обработки;
  исключение только записывается как `instagram.batch.failed`.
- `lifespan`: остановка отменяет фоновые задачи и очищает пакеты.
- `src/db/pending_messages.py`: постоянная очередь содержит только готовый
  исходящий текст и не связана с исходными входящими MID.
- `_dispatch_user_event` и обработчики не возвращают явный результат, который
  отличал бы доставленный ответ от паузы, молчаливой передачи или ошибки.

Основание: чтение локального кода и независимое read-only исследование
`handoff_explore`; для этой задачи сервер не изменялся.

## Требования

### FR-1. Сохранение до подтверждения приёма

WHEN приходит корректно подписанное входящее событие с MID, система SHALL
сохранить необходимые для обработки данные и MID в постоянном хранилище до
HTTP 200. IF сохранение не удалось, система SHALL не подтверждать успешный
приём. Повторная доставка того же MID после перезапуска SHALL не создавать
вторую задачу. Существующие правила проверки подписи и неподдерживаемых
событий сохраняются; сообщения без MID не запускают новую обработку.

### FR-2. Явный результат обработки

Для каждого принятого события система SHALL различать как минимум: ожидание,
активную обработку, повтор после ошибки, доставленный ответ, готовый ответ
в исходящей очереди, молчаливую передачу с возможностью пересмотра, обязательную
передачу человеку, перехват менеджером, намеренное игнорирование и неопределённую
доставку. Отсутствие записи assistant само по себе SHALL не считаться потерей.
Связь результата с исходными MID SHALL сохраняться при объединении сообщений.

### FR-3. Восстановление после технического сбоя

WHEN обработка оборвалась до доставки или постановки готового ответа в очередь,
система SHALL восстановить задачу после запуска либо очередной проверки,
сохранив исходный вопрос и допустимый порядок событий одного клиента.
Невалидный/обрезанный ответ модели, ошибка его схемы и исключение модели,
завершившиеся технической молчаливой передачей, SHALL также относиться к FR-3,
даже если исключение обработано и функция вернула управление штатно.
Активная медленная обработка медиа, голосового или модели SHALL не запускаться
повторно параллельно. Отмена при остановке SHALL не стирать принятые события.
Повторы SHALL ограничиваться предложенными выше пределами. Исчерпание повторов
SHALL иметь наблюдаемый результат и использовать существующий маршрут ошибки
к менеджеру с защитой от повторного уведомления по FR-4.

### FR-4. Пересмотр молчаливой передачи

WHEN модель молча передала запрос менеджеру, включая рекламный отклик, система
SHALL один раз повторно передать вопрос модели через 120 секунд с актуальным
контекстом диалога. Техническая передача из FR-3 SHALL использовать счётчик
технических повторов вместо дополнительного повтора по FR-4.
Понятность запроса SHALL определять DeepSeek, без списка
разрешённых названий туров. Исходный рекламный или медийный контекст SHALL
оставаться связанным с исходным вопросом; контекст другого объявления не
подставляется. Повтор SHALL не дублировать входящую реплику в истории.

IF повторный разбор позволяет ответить, система SHALL отправить ответ обычным
маршрутом. IF снова требуется менеджер, система SHALL сохранить передачу без
второго подтверждённо доставленного Telegram-уведомления и повторного увеличения
счётчика эскалаций по той же заявке. Эта защита SHALL действовать также для
служебного блока эскалации внутри повторного ответа модели.
Неуспешная отправка уведомления, ограничение уведомлений и неопределённая
доставка SHALL различаться с успешной доставкой; последняя не предполагается
по факту вызова функции. Повторы уведомлений SHALL соблюдать существующие
лимиты; неопределённая отправка SHALL не повторяться вслепую.
Недоступность медиа SHALL обрабатываться штатным безопасным маршрутом, без
выдуманного содержимого и бесконечных повторных скачиваний.

### FR-5. Приоритет менеджера и свежей переписки

IF менеджер ответил или действует пауза после менеджера, система SHALL
не отправлять восстановленный ответ. Это условие SHALL проверяться также
после медленной обработки непосредственно перед отправкой.
Снятие паузы само по себе SHALL не оживлять старые перехваченные менеджером
заявки. WHEN пришли новые сообщения, система SHALL учесть их по порядку;
IF исходный вопрос уже покрыт последующей обработкой, второй ответ на него
SHALL не отправляться. Покрытие SHALL определяться связью с входящими
сообщениями, а не только временем последнего ответа в истории.

### FR-6. Сохранение обязательных человеческих маршрутов

Молчаливые story mention и доказанные приглашения соавтора SHALL оставаться
у менеджера. Файлы и товарные карточки SHALL сохранять текущий маршрут
к менеджеру. Игнорируемые GIF/стикеры и служебные телефонные template SHALL
не становиться причиной восстановления или дополнительного ответа, если они
пустые либо дублируют номер в основном сообщении. Самостоятельная распознанная
карточка с новым номером SHALL восстанавливаться как обычное контактное сообщение.
Пересмотр из FR-4 применяется к решению модели, а не отменяет эти правила.
Обычные истории, фото, Reels, смешанные карусели, прямое видео и голосовые
SHALL сохранять действующую обработку; пятисекундная группировка сохраняется.

### FR-7. Защита от повторной отправки

IF ответ уже доставлен, система SHALL не генерировать и не отправлять его
повторно. IF готовый ответ находится в исходящей очереди, система SHALL
продолжить его доставку через эту очередь, без нового запроса к модели.
Частично доставленный ответ SHALL не начинаться повторно с первой части.

IF процесс оборвался во время внешней отправки или сетевой результат не
позволяет установить доставку, система SHALL зафиксировать неопределённый
исход и направить его на проверку вместо слепой повторной отправки.
Гарантия «ровно один ответ» при недоступном подтверждении внешней системы
не заявляется. Существующие исходящие записи SHALL не теряться при обновлении.

### NFR-1. Наблюдаемость, данные и границы запуска

Журнал SHALL позволять определить причину и число повторов, итог и связь
с исходным MID без токенов, подписанных URL и полного текста переписки.
Постоянное хранилище SHALL содержать только необходимые для восстановления
данные, без дополнительной постоянной копии медиа. Политика очистки завершённых
записей SHALL быть определена в Design до реализации; незавершённые задачи
не удаляются как успешно обработанные.

Восстановление SHALL охватывать сообщения с исходным временем после сохранённой
границы включения функции, включая обнаруженные API после простоя сервера.
Более ранняя историческая переписка автоматически не переигрывается.
Проверки реализации SHALL использовать изолированные данные и заглушки
отправки/модели. Выкладка, реальные тестовые сообщения и сброс клиентских
данных не входят в текущую локальную реализацию.

### FR-8. Восстановление пропущенных webhook через Conversations API

WHEN бот запускается после включения функции либо наступает интервал
120 секунд, система SHALL сверять доступную переписку Instagram через
официальный Conversations API. Список диалогов SHALL включать ещё неизвестных
боту клиентов; обход только существующих сессий недостаточен. Найденные новые
сообщения SHALL сохраняться в ту же очередь, что и webhook, до продвижения
контрольной точки сверки. Одинаковый MID из двух источников SHALL не создавать
вторую задачу; известный MID SHALL не считаться доказательством успешного ответа.

Проверка SHALL учитывать входящие и исходящие сообщения, сохранённые ID ответов
бота и менеджерский перехват. Неопределённая принадлежность исходящего сообщения
SHALL не трактоваться как доказанный ответ бота или менеджера. Переписка SHALL
обрабатываться в хронологическом порядке, с сохранением границ разных источников
историй/рекламы и группировки из FR-6.

IF API не возвращает необходимые данные, система SHALL фиксировать неполноту
и применять FR-3/FR-6/FR-7 по фактической причине, без выдумывания содержимого.
Ограничение деталей двадцатью последними сообщениями SHALL учитываться отдельно
от возможности перечислять более старые ID. Пагинация SHALL не объявляться
способом восстановить недоступное старое содержимое.

Ошибка API или лимит SHALL не останавливать обычный webhook и локальную очередь;
сверка SHALL иметь ограниченный бюджет запросов, таймауты и задержку повторов.
Полный цикл сверки SHALL не объявляться успешным при пропущенной странице или
диалоге. При первом включении SHALL фиксироваться начальная граница без
автоматических ответов всей исторической переписке. Временные границы и запрет
автоматического ответа вне допустимого окна Meta SHALL учитывать исходное время
сообщения клиента, а не время его обнаружения нашим сервером.

Обычная сверка SHALL не вызывать DeepSeek. Вызов модели допустим для реально
восстанавливаемой заявки либо предусмотренного FR-4 пересмотра.

## Проверка официального API

По официальной документации Conversations API позволяет перечислять диалоги,
получать ID/время сообщений и детали сообщений; детали ограничены двадцатью
последними сообщениями диалога. Полнота полей рекламы/историй/вложений и
совпадение ID с нашим webhook требуют проверки на текущем подключении.

Источники:
- https://developers.facebook.com/documentation/business-messaging/messenger-platform/conversations.md
- https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/conversations-api

Живая проверка SHALL быть read-only: без ответов клиентам, вызовов DeepSeek,
изменения кампаний, токенов, прав, сессий и запуска бота. Вывод SHALL содержать
только технические признаки доступности и обезличенные результаты, без текста
переписки, полных ID, CDN-ссылок и секретов. Пробные неподдерживаемые API-поля
SHALL отличаться от отказа в доступе и от недоступного старого сообщения.

Факт проверки 2026-10-15: локальный сохранённый PAGE-токен позволяет читать
список диалогов, участников, ID, время, отправителя/получателя и текст сообщений.
Поля `attachments`, `shares`, `reply_to`, `story` принимаются API; фактического
содержимого вложений/историй в ограниченной выборке не было. Поле `referral`
у Message API отвергается как несуществующее (код 100). Совпадение локального
токена с текущим серверным и точное совпадение API ID с production webhook MID
не подтверждены. Полный локальный `.env` не совпал с fingerprint последней
выкладки; это само по себе не доказывает различие токенов. SSH до выполнения
серверной проверки не подключился. Подробности: `runtime/instagram-inbound-recovery.md`.
