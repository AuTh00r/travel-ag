# Единый JSON модели — N28

2026-10-16. Status: выложено и проверено. Спека:
.kiro/specs/media-understanding, Quick N28; ADR0005-unified-model-json accepted.

## Симптом и причина

ADS использовал decision/reply/context, остальные маршруты — свободный текст с
маркерами. Даже ADS требовал блок менеджера внутри reply. Реальный провайдер
пропускал context; прежний контракт смешивал клиентский текст и действие.

## Решение

Один объект {reply:string,manager:null|{context:string,type:string,name:string}}
для каждого ainvoke. Никаких decision/reason/phone или новых маркеров действий.
Текст и vision всегда JSON object mode; строгий общий валидатор проверяет ключи,
дубликаты, типы, лимиты и маркеры. В manager.context — короткая выжимка до450
символов, type=консультация/контакт/отзыв, name до100символов. Входные сообщения
и история остаются данными, последний user/media сохраняется при повторе.

Три исхода: ответ; ответ+менеджер; молчаливая передача неясного ADS. Пустой reply
обычного запроса запрещён. Один общий повтор по ошибке формата/пустому ответу,
всего максимум2вызова. Truncation/oversize/non-string/provider error терминальны.
Финальная ошибка даёт техническую эскалацию: ADS молчит, обычный запрос получает
честный фиксированный ответ. Фактическое подтверждение зависит от Telegram receipt.
Программные media/guard/STT fallback не JSON-парсятся. В клиентский канал/assistant
history идёт только реально доставленный текст. Старые маркеры очищаются из
prompt history; разбор свежих manager-маркеров удалён. Бронь остаётся ссылкой.

Номер берётся из текущего ввода. Дополнительно сохранён номер внутри фразы
(явный international/BY, однозначный), typed text сильнее STT. В контексте
удаляется только известный номер, сохраняются текущий тур/даты/бюджет; чистая
контактная подпись сохраняет тему предшествовавшего разговора. Общее «Я хочу…»
не считается именем. Номер из model output не принимается; неоднозначность
не угадывается. Паузу менеджера/лимиты/пять секунд сбора/медиа не меняли.
