# Свежесть recovery-диалога отстаёт при работающем сканере

## Symptom

В allowlist с одним клиентом `scan_failures=0`, интервал 120 секунд, но
checkpoint диалога отстал более чем на четыре часа. Общий cursor продолжался.
Нулевой счётчик ошибок не доказывает своевременную сверку клиента.

## Investigation / root cause

Счётчик бюджета увеличивался после каждого диалога, включая excluded без
Graph GET. Возвращение к известному клиенту зависело от полного обхода.
В воспроизведении: 1000 excluded диалогов, бюджет 60; старый код останавливался
после трёх страниц, исправленный читает 51 страницу и один нужный диалог.

## Fix

Изменяемый бюджет в ContextVar одного тика; расход внутри общего `_get`.
Known allowlist checkpoint сверяются первыми, oldest-first; discovery
продолжается с прежнего cursor. Один dialog ID читается один раз за тик,
в том числе при пересечении страниц и `gap=True`. Deadline завершает тик
штатно; ранние сетевые ошибки и rate-limit сохраняют provider backoff.
Непрочитанный элемент не удаляется. Независимый delivery refresh сохраняет
свой контекст и общий limiter. Новых таблиц/флагов нет.

## Verification

15 изолированных регрессий, полный pytest 1431 PASS/8 прежних warnings,
Ruff/diff PASS, независимое review закрыто. См. TSK-020 и ADR 0012.
Новый API MID после simulated restart достигает обычного worker и одного
подтверждённого ответа; внешние отправки и модель заменены заглушками.

Выкладка отдельно разрешена 2026-10-18: один runtime-файл, 29 SHA/health
PASS, новый PID6872. Живые priority checkpoint (UTC) 14:33:05.781909 →
14:35:06.028029, интервал 120.246 с. Baseline/env/тестовая сессия сохранены;
нет активных/зависших задач и unknown отправок. Откат проверен с сохранением
новых receipts; рабочая БД не заменялась.

## Limits

Интервал зависит от API,
rate-limit и достаточного бюджета. При allowlist больше бюджета oldest-first
обслуживает известных клиентов по очереди; discovery использует остаток.
Проверка API-only медиа и проблема подписи webhook — отдельные ограничения.
Живая страница API содержала 21 запись при limit=20; все 21 MID уже в журнале,
но выложенная консервативная проверка размера/адаптер оставляют gap=True.
Свежий checkpoint подтверждает polling, а не полное покрытие всей истории.

## Локальное продолжение: полная страница и message cursor

2026-10-18, TSK-021/ADR 0013: убран slice 20. Все фактические записи
сохраняются до continuation; JSON checkpoint хранит after, фиксированный
верх окна и dirty. Новая голова читается первой, старый хвост продолжается
после restart. Отделённая новая голова не поднимает through через непрочитанный
интервал; равное время требует следующей страницы. Некорректный cursor
сбрасывает только продолжение диалога. Scanner и delivery refresh используют
отдельный sync lock и ограниченный бюджет.

Проверено локально: 23 новые регрессии с настоящей временной SQLite,
1454 PASS/8 прежних warnings, Ruff/diff и независимое review PASS.
Модель, API и внешние отправки заменены заглушками. Затем по отдельному
«деплой» установлен совместный пакет4 (1480 PASS), PID4136/29 SHA/health PASS.
Живой message after проверен: голова21, следующая страница19, gap=false,
baseline/env/тестовая сессия сохранены. При бюджете одного GET хвост не продвигается:
минимум два GET нужны после обязательной свежей головы. Штатный лимит 100.
Это исправляет покрытие сообщений, но не возвращает содержимое медиа,
которое Meta пометила unsupported.
