# Instagram: раннее собственное эхо включает manager takeover

Проверено 2026-10-10. Симптом: после разрешённого снятия паузы бот вновь перестаёт отвечать; новое голосовое пропускается до распознавания.

Evidence: reset08:27:43Z, новое manager.detected09:33:57.498Z, takeover09:33:57.507Z, отправка собственного ответа завершена09:33:57.920Z. В тестовой истории собственный ответ о вложении сначала записан обработчиком менеджера без тега, затем тем же текстом с ожидаемым служебным тегом обработчика non-text. INSTAGRAM_APP_ID не настроен. Это раннее эхо до получения message_id, а не новое сообщение человека. Read-only просмотр ограничен собственным тестовым аккаунтом; номера/URL из текста редактировались.

Root cause: кеш известных отправленных MID заполнялся после await HTTP post. Webhook может прийти во время этого await. Такой MID ещё неизвестен и поэтому считался сообщением менеджера.

Fix: счётчик незавершённых отправок по точному получателю и фактически отправленному (уже обрезанному) тексту; регистрация до сетевого await, очистка в finally при успехе/ошибке/отмене. Совпадающий ранний webhook пополняет прежний ограниченный MID-кеш. Явный чужой app_id при известном нашем app_id запрещает fallback. После завершения отправки новый MID с тем же текстом по-прежнему включает паузу. Нет общего игнорирования сообщений менеджера на несколько секунд.

Verification:5 regressions before fix FAIL→afterfix PASS; полный714pytestPASS, Ruff/diff-checkPASS, read-only review clear. На сервере изменён только Instagram source, резервная копия source+manifest SHA проверена. Все20 source entries/launcher/env verified, listener7116→14396, local/publichealthok. Deployed-channel proof проверил раннее эхо и сохранение manager events, без настоящих клиентских отправок. Разрешённый admin reset изменил только manager_last_at; история и escalation_count3 сохранены.

Live: новая запись владельца в Instagram14:16:27Z, вопрос про наличие тура в Сербию распознан и сохранён с marker; ответ отправлен14:16:40.957Z. После ответа manager_last_at=null, сервисного менеджерского блока нет. Это проверка реального входящего голосового/ответа, а не повторное проигрывание сохранённого файла. Telegram-уведомление этим тестом не проверялось: счётчик3 специально сохранён по указанию владельца.

Границы: точное совпадение одинакового текста от реального менеджера тому же клиенту именно во время незавершённой отправки при отсутствующем app_id неотличимо от раннего эха. Поздние неизвестные MID после рестарта не входят в этот фикс. Выставленный корректный INSTAGRAM_APP_ID остаётся дополнительным штатным способом определить источник. Не выводить credentials/signed media URLs; не хранить полный payload для такой диагностики.

Operations: не заменять локальный deployment manifest вслепую. Автопроверка заблокировала прямой overwrite; read-only diff показал20 одинаковых имён и единственную изменённую запись Instagram source. Сделана проверенная локальная резервная копия, обновлены лишь sha256/bytes разрешённого файла. Ошибка PowerShell property-collection Count устранена явным массивом имён, повторная сверка PASS.
