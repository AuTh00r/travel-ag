# Instagram ADS: пустой ответ модели в JSON-режиме

Дата: 2026-10-15. Статус: read-only диагностика; runtime не изменён.

## Симптом

Заявка с понятным вопросом «Виза есть! Пришлите программу тура ВДП» передана
менеджеру с причиной «неверный формат ответа». Рассматриваемый случай:
15.10.2026 22:27 Минск / 19:27 UTC.

## Проверенные факты

Удалённый Python выполнялся с `-B`, без импорта приложения и без записи файлов.
Читались ограниченные фрагменты текущего журнала; профиль сверялся GET-запросом
Meta только для привязки единственного события к заявке. Вывод содержал
технические признаки и хэш идентификатора, без токенов/переписки/URL медиа.

SHA main.py и llm.py совпали с установленным N24.

| Время Минск | Событие |
| --- | --- |
| 22:26:54 | Получены referral source=ADS и сообщение |
| 22:26:59 | Пятисекундный batch: received=1, dispatched=1 |
| 22:27:03 | instagram.ad.invalid_model_decision, reason=empty_response |
| 22:27:05–07 | Подтверждены отправки уведомления Telegram |

Метаданные отклонённого ответа: finish_reason=stop, response_kind=text,

## Причина и границы вывода

В N24 `_process_with_ai` передаёт response.content непосредственно в
`_validate_ad_response`. Причина empty_response появляется только когда
строка пуста после strip(), до JSON-парсинга. Поэтому по коду и метаданным
242 символа состояли из удаляемых strip() пробельных символов. Сырой ответ
не логируется и задним числом не извлечён.

Это не валидное модельное решение handoff и не вывод, что запрос непонятен.
Признака остановки по лимиту вывода нет: finish_reason=stop, не length.
Конкретную внутреннюю причину пустой генерации провайдера эти логи не раскрывают.

JSON mode в существующих ADS-фабриках включён; он не гарантирует непустое
содержимое. Официальная документация DeepSeek прямо предупреждает о редких
empty-content ответах JSON Output и предлагает корректировать prompt.

Application не делает повтор генерации при успешном API-ответе с пустым
содержимым, а сразу вызывает техническую молчаливую передачу. Именно этот
путь объясняет полученное уведомление. Transport-retries SDK этого случая
не покрывают, так как ошибка содержимого обнаружена после получения ответа.

## Воспроизведение и дальнейшее действие

Из текущего main AST извлечён только validator, без импорта приложения.
Синтетическая строка из 242 пробельных символов даёт empty_response;
контрольный JSON с decision/reply/context принимается. Это проверка ветви
программы, а не повтор реальной генерации DeepSeek.

Предлагаемая отдельная минимальная защита: один дополнительный вызов модели
только при пустом содержимом, с сохранением JSON-контракта и проверками
менеджерского перехвата. Если второй ответ непригоден — прежняя техническая
передача. Изменение prompt само по себе не является доказанной гарантией.
На момент диагностики реализация, платные повторные запросы и replay клиентской
заявки не выполнялись. Последующее исправление описано в N25 ниже.

Дополнительный обезличенный контроль журнала N24 20:36–22:31 Минск:
зарегистрированы empty_response=1 и invalid_fields=1. Количество успешных
запросов не измерялось, поэтому частота ошибок/процент не рассчитываются.
Другой invalid_fields не приписывается этой заявке.

Источник: https://api-docs.deepseek.com/guides/json_mode

## N25: локальное исправление по «исправь» (2026-10-15)

Спека записана до кода. Только первый empty_response без finish_reason=length
получает один повтор тем же model instance и messages, без повторной подготовки
медиа/добавления истории. Непустой невалидный JSON, truncated и provider error
не запускают дополнительный вызов. Ответ второй попытки идёт через прежний
строгий контракт; повторная ошибка вызывает одну техническую передачу с реальной
последней причиной. Перед повтором и применением результата проверяются pending
и сохранённая пауза менеджера; отмена задачи распространяется без уведомления.

Второй ответ модели не гарантирован. Максимум два прикладных ainvoke, при этом
существующие настройки транспортных повторов SDK не менялись (vision: 0;
text: прежняя настройка). На повторе не используются пустой ответ модели или
текст предыдущих служебных ошибок как новые сообщения в prompt.

Проверка до фикса: 21red/4green. Независимое ревью нашло сохранённую паузу во
время provider exception при лимите3: новый тест подтвердил потерю manager_last_at
(1red/1green); общий свежий ADS guard после try/except исправил это. Финальные
90targetedPASS, включая31 новый case. Финальная полная QA:1009PASS/8прежних
предупреждений/36.25s; Ruff/diff/micro-spec checkPASS, повторное read-only ревью
без замечаний после исправления случая с паузой менеджера.

Архитектурная запись через CLI: .kiro/decisions/0002-ad-empty-response-retry.md,
review5/6, accepted. Никаких серверных изменений, replay заявки, реальных
клиентских/менеджерских отправок или платных пробных вызовов модели.
