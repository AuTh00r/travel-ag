# Четыре отказа рекламы и один неопределимый диалог

## Симптом

После выкладки20Oct15:08 Минск до19:33: четыре ad_lookup HTTP400/code100/subcode33
и три incomplete_identity. Сбоев самого reconcile/модели/доставки в этом окне
не обнаружено. Тестер сверяется с персональным gap=false, очереди пусты.

## Проверка рекламы

Четыре события относятся к четырём клиентам и двум рекламным ID: одно
объявление встречается один раз, другое трижды. В каждом35-секундном окне
был ровно один уникальный referral/client, поэтому связь не выбиралась наугад.
Все referral содержали text и photo_url, без video_url и post/permalink source.
После отказа Marketing API обработчик использовал clicked_asset image.
В каждом случае подготовлена1 картинка, маршрут модели ad_vision, valid
tool_calls с первой попытки, reply622–688 символов, manager=null. Следом
для того же клиента есть instagram.message.sent, ошибок отправки не найдено.

Живые read-only Graph проверки: ads_read granted/HTTP200; все3 настроенных
рекламных кабинета доступны/HTTP200 с совпадением account_id. Два конкретных
ad ID повторно вернули100/33 с Unsupported get request и общим указанием
на отсутствие объекта/доступа/поддержки операции. Это не доказывает конкретно
удаление объявления или конкретно нехватку разрешений. Глобальная невалидность
токена и отсутствие ads_read этим контролем исключены.

Клиентские заявки в этих4 случаях не потерялись. Но исходный creative и полное
видео не получены: ответ построен по картинке из referral и тексту. Разумно
отдельно диагностировать ad_lookup failure и успешный fallback, сохраняя
предупреждение о неполном медиа. Новых разрешений по предположению не выдавать.

## Контроль по ID пользователя, 20 октября

Тем же токеном бота четыре уникальных ID 120255975144020322,
120255975235320322, 120255975252250322, 120255975270710322 вернули HTTP200,
точный id, настроенный account_id и ACTIVE/ACTIVE. Объявление
120255819105930322 «Рилс ВДП Рождество» также HTTP200, PAUSED/PAUSED.
Два проблемных ID 120255975320400322 и 120255975320430322 повторно 100/33.
Следовательно, выключение само по себе не делает объявление нечитаемым.

Все пять доступных объявлений принадлежат одной группе «РБ» кампании
«ВДП декабрь 2026». GET этой группы /ads вернул ровно эти пять записей,
без следующей страницы; проблемных ID в этом ответе нет. Это не устанавливает
их принадлежность или отсутствие во всех прочих группах/статусах.

У всех четырёх активных creative есть asset_feed_spec с двумя вариантами медиа
и двумя asset_customization_rules; optimization_type=PLACEMENT. У первых двух
варианты videos, у последних двух images. Сам adset is_dynamic_creative=false:
эти два признака не следует смешивать. У выключенного creative asset_feed_spec
отсутствует. Имена referral 4_Group_1/4_Group_1_Image не совпали с возвращёнными
именами ads или labels; точная связь с исходными объявлениями не доказана.

Найдено отдельное ограничение текущего resolve_ad_media: непустой asset_feed_spec
безусловно вызывает ad_unproved_creative, даже при доступном ad/creative и
Instagram permalink. Поэтому HTTP200 этих четырёх ID не означает, что текущий
бот восстановит точный выбранный вариант через Marketing API. Проверена ветка
кода, живую обработку клиента не запускали. Сервер не меняли.

Evidence: provided-ad-id-comparison, provided-ad-metadata, provided-adset-ads,
provided-ad-customization в прежнем каталоге локальных артефактов.

## Проверка неопределимого диалога

Все3 предупреждения имеют один fingerprint и одну запись dialog_gap.
Прямой GET этого conversation с fields=id,participants вернулHTTP200:
participants.data содержит ровно1 непустой строковый ID — настроенный IG ID
самой компании. Другого участника и participants.paging.next нет.

После исключения собственного ID остаётся0 клиентов; текущий sync_dialog
закономерно выдаёт ambiguous_participants. Причина не в дублях или третьем
alias собственного аккаунта. Почему Meta не раскрыла второго участника,
по этим данным не установлено; сообщения чужого диалога не запрашивались.

Проверка личности выполняется до allowlist. Общий проход помечается incomplete,
но элемент пропускается, остальные диалоги продолжаются; known tester checkpoint
проверяется первым. complete_scan не обновляется, однако доставка зависит
от персонального refresh_client. Само предупреждение не блокирует тестера.

Для такого состояния нельзя придумывать адресата или объявлять полный охват.
Можно отдельно показывать identity gap и ограничить повтор одинакового
предупреждения, продолжая метаданные перепроверять. Это рекомендация, не фикс.
