# Лишние и повторные задачи менеджеру

Symptom: бот передавал менеджеру обычное уточнение тура, уже предложенные визовые
альтернативы и повторные детали существующего вопроса. Встречались утверждения
об отсутствии Белостока, хотя опубликованный каталог содержал даты.

Investigation: read-only аудит21модельного решения после N36 отделил6лишних
передач и3уточнения от самостоятельных нерешённых вопросов. Каталог источника и
результат парсера не доказали, какой именно текст получил прошлый запрос модели:
промпт тогда не логировался. Причина конкретной ошибки Белостока остаётся
неподтверждённой; не выдавать гипотезу о кэше за факт.

Root cause: в prompt оставалось прямое противоречие — обычное уточнение названия
тура требовало manager. Полученный manager исполнялся без независимой смысловой
проверки; у уведомлений не было постоянного ID нерешённого вопроса и связанных
Telegram message IDs для последующих уточнений.

Fix: основной reply/manager сохранён. Один ограниченный review_handoff проверяет
только валидного кандидата на обычную консультацию: cancel/new/update. Ошибка
проверки оставляет исходный ответ; manager takeover отменяет старую обработку.
Обязательные маршруты bypass review. Из точного tours_text сохраняются хеш,
имена и даты доступности, отдельно для primary/review с parent_request_id.

Открытые вопросы и версии находятся в SQLite, вне session JSON. Recovery пишет
изменение задачи и outbox одной транзакцией. Legacy сохраняет intent до HTTP;
его worker повторяет только известные неотправленные операции. Partial4chat,
unknown и перезапуск обрабатываются отдельно. Edit использует только свой
подтверждённый chat/message ID; неудачный edit не заменяется новым send. Первый
подтверждённый вопрос увеличивает счётчик один раз; уточнение его не увеличивает.
После ответа менеджера прежняя задача закрыта даже после снятия паузы.

Verification:1594pytest PASS,8preexisting warnings, Ruff/diff PASS. Настоящий
SQLite и HTTP/SDK mocks;21синтетический сценарий, callback/CAS/restart/partial/
unknown/limit/takeover, legacy count и coexistence с recovery. Старые receipts
сохраняются при миграции. Первые3native decoder failures вызваны PowerShell
песочницы; полный повтор в обычной среде с отдельным temp PASS, политика не менялась.
Независимый read-only review выявил два пробела (legacy retry worker и неполный
API-контекст проверяющей модели); исправлены до финального полного прогона.

Limits: это доказательство программных маршрутов, не семантики DeepSeek и не
живой доставки Telegram. Последующий отдельный paid evaluation из 19 вызовов
получил 19 валидных форматов и 17 совпадений action, но пять подтверждённых ошибок
задач: неверные cancel 2/10, подмена вопроса 14, придуманная дата 19, потеря темы 21.
Все URL найдены в каталоге. Прогон НЕ прошёл семантическую приёмку. После этого
локально уточнены условия cancel/new и контекста; review переиспользует общие
business/link/closing blocks без primary transport. 1597 pytest/Ruff/diff PASS.
Отдельно разрешённый повтор 9 случаев дал 9 валидных ответов и 9 ожидаемых решений;
ручная независимая проверка подтвердила исправление пяти прежних дефектов задач,
сохранение контактной строки и канонических ссылок программ. В сумме использованы
28 вызовов в двух разрешённых бюджетах 19+9. Неблокирующие наблюдения: сокращённый
список каталога в случае 10 звучит слишком категорично; в 2/4 ссылка стоит после
вводного описания. Эти наблюдения не выдаются за исправленные.
Повтор проверяет reviewer, а не всю живую обработку или Telegram-доставку;
не все первоначальные случаи повторялись на последнем промпте.
