## Контекст

Проект — Telegram/Instagram-бот турагентства (`travel-agent-bot`). Канал
Instagram Direct реализован в `src/channels/instagram.py` и работает через
**Meta Graph API** напрямую по HTTP (без официального SDK):

```python
# src/channels/instagram.py:17-19
class InstagramChannel(ChannelBase):
    """Канал Instagram Direct через Meta Graph API."""
    BASE_URL = "https://graph.facebook.com/v25.0"
```

Через этот `BASE_URL` идёт и отправка сообщений (`send_message`), и получение
username клиента (`get_username`). Это единственная точка интеграции с Meta в
проекте.

Сейчас у бота **нет** обработки ситуации, когда Meta ограничивает частоту
запросов (rate limiting), и **нет** видимости в лог, если сообщение клиенту
реально не дошло. Ниже — что именно нужно сделать и почему.

### Как Meta сигнализирует о rate limit (проверено по офиц. докам Meta, июль 2026)

Источник: `https://developers.facebook.com/docs/graph-api/overview/rate-limiting`

- Throttling **не** сигнализируется отдельным HTTP-статусом (не 429) — код
  ошибки приходит **внутри JSON-тела ответа**, в поле `error.code`.
- Актуальные коды:
  - `4` — превышен лимит на уровне приложения (app-level)
  - `17` — превышен лимит на уровне пользователя (user-level)
  - `32` — превышен лимит Pages API
  - `613` — кастомный/self-defined лимит
  - **`80002`** — Business Use Case (BUC) лимит **именно для Instagram**
    (более приоритетный слой лимитов; если применимы оба — action по BUC)
  - `80006` — BUC-лимит для Messenger (для справки, у нас не Messenger, но
    похожая механика)
- Заголовки ответа, которые Meta присылает для мониторинга нагрузки:
  - `X-App-Usage` — JSON с `call_count` / `total_cputime` / `total_time` в
    процентах (platform-level).
  - `X-Business-Use-Case-Usage` — JSON с той же структурой + поле
    **`estimated_time_to_regain_access`** — сколько **минут** ждать до снятия
    троттлинга. Это функциональный аналог `Retry-After`, но в кастомном
    заголовке, а не в стандартном HTTP-заголовке.
- Официальная рекомендация Meta: **не повторять запросы сразу после отказа** —
  это только продлевает штрафной период. Нужно проактивно следить за
  заголовками usage и не доводить до жёсткого отказа.

### Что сейчас происходит в коде при сбое отправки

```python
# src/channels/instagram.py:256-279 (send_message)
async with httpx.AsyncClient(timeout=30) as client:
    try:
        response = await client.post(url, params=params, json=payload)
        response.raise_for_status()   # <-- проверяет только HTTP-статус
        ...
    except httpx.HTTPStatusError as exc:
        raise InstagramError(...) from exc
    except httpx.RequestError as exc:
        raise InstagramError(...) from exc
```

`response.raise_for_status()` реагирует только на HTTP 4xx/5xx. Если Meta
вернёт формальный HTTP 200 с `error.code` в теле (так бывает) — код это не
поймает и посчитает сообщение отправленным.

Дальше, в `src/main.py`, ошибка `send_message` просто логируется и **сообщение
клиенту теряется молча**, без ретраев:

```python
# src/main.py:338-343 — основной ответ от AI
for chunk in _split_reply(clean_reply):
    try:
        await instagram.send_message(sender_id, chunk)
    except Exception:
        logger.exception("instagram.message.send_failed", sender_id=sender_id)
        break
```

Аналогично без ретраев в `main.py:463` (ack после non-text сообщения) и
`main.py:487` (фолбэк-сообщение об ошибке).

Также нет **общего** ограничения исходящего потока к Meta: `is_rate_limited()`
из `src/services/guard.py:69` защищает только от спама **одного** клиента
(sliding window в памяти), но никак не ограничивает суммарный поток запросов
к Graph API по всему аккаунту, если одновременно идёт несколько диалогов.

## Задача 1. Распознавать rate-limit ошибку Meta даже при HTTP 200

**Проблема:** `send_message` проверяет только HTTP-статус
(`response.raise_for_status()`), а Meta может прислать признак троттлинга
внутри JSON-тела при формально успешном HTTP-статусе.

**Действия:**
1. В `InstagramChannel.send_message` (`src/channels/instagram.py:221`) после
   получения `response` — распарсить JSON-тело **до** `raise_for_status()` (или
   независимо от него) и проверить наличие `error.code`.
2. Если `error.code` входит в множество `{4, 17, 32, 613, 80002}` — считать это
   отдельным видом ошибки (rate limit), не смешивать с прочими `InstagramError`.
   Предлагается новый класс исключения, например `InstagramRateLimitError`
   (наследник `InstagramError`, см. `src/exceptions.py`), с полем
   `retry_after_seconds: float | None`.
3. Залогировать структурированно: `logger.warning("instagram.rate_limited",
   error_code=..., recipient_id=...)`.

**Готово, когда:** тест с замоканным `httpx` ответом (HTTP 200, тело с
`error.code: 80002`) — `send_message` кидает `InstagramRateLimitError`, а не
считает отправку успешной.

## Задача 2. Использовать заголовки usage вместо слепого backoff

**Проблема:** сейчас при сбое нет повторной попытки вообще. Простой
exponential backoff вслепую — хуже, чем то, что даёт сама Meta: заголовок
`X-Business-Use-Case-Usage` содержит `estimated_time_to_regain_access` (в
минутах) — точное время до снятия троттлинга.

**Действия:**
1. При обработке ответа читать заголовки `response.headers.get("x-business-use-case-usage")`
   и `response.headers.get("x-app-usage")` (регистр заголовков в HTTP
   нечувствителен, но у Meta обычно нижний/смешанный — проверить в реальном
   ответе на этапе реализации).
2. Если заголовок присутствует — распарсить JSON, вытащить
   `estimated_time_to_regain_access` (может быть вложен по ключу
   business-object-id — см. структуру в реальном ответе перед реализацией,
   т.к. в документации формат ключей не показан явно на примере). Положить
   значение в `InstagramRateLimitError.retry_after_seconds` (перевести минуты
   в секунды).
3. **Не делать ретрай внутри `send_message` синхронно, ждать в цикле** — это
   заблокирует `asyncio`-таск на минуты. Вместо этого:
   - `send_message` кидает `InstagramRateLimitError` с `retry_after_seconds`.
   - Вызывающий код (`main.py`, п. Задача 3) решает, что делать: либо
     логировать и не пытаться повторно в рамках этого запроса (проще,
     рекомендуется как MVP), либо (расширенная версия) поставить
     отложенную повторную отправку через `asyncio.sleep(retry_after_seconds)`
     в отдельной фоновой задаче — **только если** `retry_after_seconds`
     разумно мал (например, < 60 сек), иначе просто эскалировать в Telegram
     менеджеру, что клиенту не удалось ответить.
4. **Не спамить повторными запросами**, пока не истечёт время из
   `estimated_time_to_regain_access` — это прямая рекомендация из документации
   Meta (повторные запросы во время троттлинга продлевают штраф).

**Готово, когда:** есть тест, что при `InstagramRateLimitError` с
`retry_after_seconds` код не делает немедленный повторный HTTP-запрос.

## Задача 3. Не терять сообщения клиенту молча

**Проблема:** во всех трёх местах отправки в `main.py` ошибка `send_message`
ловится через `except Exception` и просто логируется как `.exception(...)` —
дальше ничего не происходит, клиент не получает ответ, и никто, кроме того,
кто читает логи построчно, об этом не узнает.

Места:
- `main.py:338-343` — основной ответ от AI (`process_with_ai`)
- `main.py:463` — ack после non-text сообщения (`_process_non_text_safely`)
- `main.py:487` — фолбэк "техническая ошибка" (`_process_safely`)

**Действия:**
1. Завести единый лог-маркер для случая "клиенту ничего не ушло":
   `logger.error("instagram.message.lost", sender_id=..., reason=...)` —
   именно `.error`, не `.exception`, чтобы отличать от прочих трейсбэков и
   можно было настроить алерт по этому событию отдельно.
2. Различать причину в `reason`: `"rate_limited"` (поймали
   `InstagramRateLimitError` из Задачи 1) vs `"other"` (сетевая ошибка,
   невалидный токен и т.п.).
3. Опционально (обсудить перед реализацией, не обязательно для MVP): при
   потере основного ответа клиенту — эскалировать в Telegram менеджеру через
   `TelegramNotifier.notify_manager(...)` с пометкой "бот не смог ответить
   клиенту", чтобы менеджер написал вручную. Это то же самое, что уже
   делается для non-text сообщений (см. `main.py:398-405`), просто с другим
   триггером.

**Готово, когда:** в тестах на сбой `send_message` (уже есть заготовки в
`tests/test_instagram.py`, класс `TestInstagramChannelSend`) проверяется
именно структурированный `logger.error("instagram.message.lost", ...)`, а не
просто отсутствие исключения наружу.

## Задача 4. Починить эвикцию `_sent_mids` (мелкий баг, попутно)

**Проблема:** `_sent_mids` — обычный `set[str]`, используется, чтобы отличать
echo от **собственных** сообщений бота (см. `is_own_message`,
`src/channels/instagram.py:281-285`) от echo **живого менеджера**. При
переполнении чистится так:

```python
# src/channels/instagram.py:268-271
self._sent_mids.add(mid)
if len(self._sent_mids) > self._SENT_MIDS_MAX:
    for _ in range(len(self._sent_mids) - self._SENT_MIDS_MAX):
        self._sent_mids.pop()
```

`set.pop()` удаляет **произвольный** элемент (по хешу), а не самый старый —
это не FIFO, как выглядит из структуры кода. На практике эффект смягчается
тем, что `is_own_message` сначала проверяет `app_id` (первичная проверка,
`instagram.py:283`) и только потом — `mid in self._sent_mids` (fallback,
`instagram.py:285`), так что баг маловероятно проявится на практике. Но раз
код это место уже трогает (Задача 1-3 рядом) — дёшево поправить сразу.

**Действия:**
1. Заменить `set[str]` на структуру с гарантированным порядком вставки —
   проще всего `dict[str, None]` (в Python 3.7+ порядок вставки гарантирован,
   это уже используется в проекте для `_username_cache`,
   `instagram.py:313-314`, где `.pop(next(iter(...)))` корректно вынимает
   самый старый ключ).
2. Обновить `is_own_message` (`instagram.py:285`) — проверка `mid in
   self._sent_mids` остаётся такой же (`in` работает и для dict, и для set).

**Готово, когда:** существующие тесты класса `TestEchoClassification`
(`tests/test_instagram.py`) проходят без изменений (поведение снаружи не
меняется), плюс новый тест: добавить `_SENT_MIDS_MAX + 1` записей, убедиться,
что вылетела именно самая старая, а не случайная.

## Принципы

- Прод-логику дедупликации/локов (`main.py`) не трогать сверх необходимого.
- Не делать синхронный `await asyncio.sleep(...)` на десятки секунд внутри
  обработчика запроса — только в отдельной фоновой задаче, и то с разумным
  верхним порогом.
- Каждая задача — отдельный коммит с понятным сообщением.
- Перед реализацией Задачи 2 — свериться с реальным (актуальным на момент
  разработки) форматом заголовка `X-Business-Use-Case-Usage` на живом ответе
  Meta API (тестовый вызов), т.к. в открытой документации точная структура
  вложенности по business-object-id не была явно показана.
