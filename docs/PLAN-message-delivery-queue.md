# План: очередь недоставленных сообщений + проактивный мониторинг rate-limit

> Статус: **план, не начат**
> Дата: 2026-07-06
> Назначение: самодостаточное техзадание, продолжение
> `docs/PLAN-graph-api-resilience.md` (тот план выполнен: детекция rate-limit
> и логирование потери сообщений). Этот план закрывает то, что там было
> сознательно отложено — реальное восстановление после сбоя доставки, а не
> только видимость проблемы в логах. Написан так, чтобы его можно было отдать
> в работу другой модели/разработчику без доступа к переписке, где он
> обсуждался.

## Контекст

### Что уже сделано (`PLAN-graph-api-resilience.md`, выполнено 2026-07-06)

`InstagramChannel.send_message` (`src/channels/instagram.py`) теперь:
- распознаёт rate-limit Meta по `error.code` в теле ответа (`4/17/32/613/80002`)
  независимо от HTTP-статуса — кидает `InstagramRateLimitError`
  (`src/exceptions.py`) с `error_code` и `retry_after_seconds`;
- `retry_after_seconds` достаётся из заголовка `X-Business-Use-Case-Usage`,
  поле `estimated_time_to_regain_access` (в минутах у Meta, у нас переведено
  в секунды).

`main.py` в трёх местах (`process_with_ai` — строка ~339, `_process_non_text_safely`
— строка ~458+, `_process_safely` — строка ~511+) ловит эту ошибку и логирует
`logger.error("instagram.message.lost", reason="rate_limited"|"other", ...)`.

**На этом всё.** Дальше ничего не происходит: сообщение клиенту не уходит,
повторной попытки нет, `retry_after_seconds` нигде не используется для
реального ожидания — только логируется.

### Найденная при этом проблема (не связана с rate-limit, существовала и раньше)

В `process_with_ai` (`src/main.py:332-339`) ответ ассистента добавляется в
историю сессии и сохраняется **до** попытки отправки:

```python
history.append({"role": "user", "content": text})
history.append({"role": "assistant", "content": clean_reply})   # main.py:333
...
await save_session(sender_id, session)                          # main.py:337

for chunk in _split_reply(clean_reply):                          # main.py:339
    try:
        await instagram.send_message(sender_id, chunk)
    ...
```

Если отправка проваливается (rate-limit или любая другая ошибка) —
**клиент не получает ответ вообще, даже фолбэк "техническая ошибка"**,
потому что исключение гасится внутри цикла (`break`) и не всплывает наружу
до `_process_safely`, чей `except Exception` как раз и отвечает за фолбэк.
При этом в истории уже лежит текст, который клиент никогда не видел — при
следующем сообщении LLM будет думать, что что-то уже сказала.

### Уточнённые факты про rate-limit Meta (проверено по офиц. докам + актуальным
источникам, июль 2026 — важно для реализации)

- Заголовок `X-Business-Use-Case-Usage` присутствует **на каждом ответе**, не
  только при ошибке — `estimated_time_to_regain_access: 0`, если лимит не
  задет. Формат подтверждён документацией Meta:
  ```json
  {"<page-id>": [{"type": "instagram", "call_count": 88, "total_cputime": 20, "total_time": 15, "estimated_time_to_regain_access": 0}]}
  ```
  Значит его можно читать **проактивно на каждом успешном запросе**, а не
  только реактивно после уже случившегося отказа.
- Признак throttling может прийти при разных HTTP-статусах (не только
  формальный 200) — наша проверка тела ответа это уже учитывает (вызывается
  до `raise_for_status()`), править не нужно.
- Широко цитируемая цифра "200 автоматических DM в час на аккаунт" —
  **не задокументированный Meta официальный потолок**, а наблюдаемое
  сообществом поведение (с окт. 2024, ранее было 5000). Реальное значение для
  конкретного аккаунта может отличаться и зависеть от его статуса/качества —
  ориентироваться нужно на заголовок usage, а не на конкретное число.
- Официального способа "запросить увеличение" именно этого лимита нет.
  Единственный легитимный путь масштабирования — несколько отдельных
  настоящих аккаунтов (не актуально для этого проекта).
- Попадание в лимит — не бан, ожидаемое поведение ("притормози"), не признак
  нарушения правил использования API.

## Задача 1. Проактивный мониторинг usage-заголовка на каждом ответе

**Проблема:** сейчас заголовок читается только когда уже поймали
`error.code` в теле. Раз `estimated_time_to_regain_access` и `call_count`
приходят всегда — можно тормозить *до* того, как Meta откажет, а не только
реагировать постфактум.

**Действия:**
1. В `InstagramChannel.send_message` (`src/channels/instagram.py`) после
   успешной отправки (там, где сейчас `logger.info("instagram.message.sent",
   ...)`) — дополнительно распарсить `X-Business-Use-Case-Usage` тем же кодом,
   что уже есть в `_extract_retry_after`/переиспользовать общий парсер, и
   залогировать `call_count`/`total_time` в процентах:
   `logger.debug("instagram.usage", call_count_pct=..., total_time_pct=...)`.
2. Завести порог (в `src/config.py`, например `instagram_usage_warn_pct: int = 85`).
   Если `call_count` или `total_time` превышают порог — `logger.warning(
   "instagram.usage.high", ...)`, чтобы это было видно в мониторинге
   заранее, ещё до реального отказа.
3. (Опционально, обсудить перед реализацией) — если `call_count` выше порога,
   можно вставлять небольшую искусственную паузу перед следующей отправкой
   (`asyncio.sleep`), чтобы размазать нагрузку. Не обязательно для MVP —
   можно ограничиться логированием и решить вопрос вручную/повышением
   порога позже, если проблема будет реальной, а не гипотетической.

**Готово, когда:** тест с замоканным успешным ответом, где usage-заголовок
показывает `call_count: 90` — в логах появляется `instagram.usage.high`.

## Задача 2. Персистентная очередь недоставленных сообщений

**Проблема:** при провале `send_message` сообщение просто теряется. Нужно
не терять его насовсем, а поставить в очередь и досылать позже — в т.ч.
переживая рестарт бота (деплой происходит регулярно, см.
`docs/DEPLOY-WINDOWS.md`, Фаза 7).

**Действия:**
1. Новый модуль `src/db/pending_messages.py` (по аналогии с
   `src/db/sessions.py`) с таблицей SQLite (та же БД `data/sessions.db` или
   отдельный файл — решить при реализации, проще в той же БД одной
   дополнительной таблицей):
   ```sql
   CREATE TABLE IF NOT EXISTS pending_messages (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       recipient_id TEXT NOT NULL,
       text TEXT NOT NULL,
       created_at TEXT NOT NULL,
       retry_at TEXT NOT NULL,
       attempts INTEGER NOT NULL DEFAULT 0
   );
   ```
   Функции: `enqueue_pending(recipient_id, text, retry_at) -> int`,
   `get_due_pending(now_iso) -> list[dict]` (сортировка по `id` — сохранять
   исходный порядок сообщений одного клиента, чтобы при досылке нескольких
   chunks одного ответа не переставить их местами),
   `mark_pending_retry(id, new_retry_at)`, `delete_pending(id)`.
2. В `main.py`, во всех трёх местах, где сейчас `except InstagramRateLimitError`
   только логирует `instagram.message.lost` — дополнительно вызывать
   `enqueue_pending(sender_id, chunk_or_reply, retry_at=now + (exc.retry_after_seconds
   or DEFAULT_RETRY_SECONDS))`. `DEFAULT_RETRY_SECONDS` — константа в
   `src/config.py` (предлагается 60, обсудить).
3. Аналогично для *любой* другой ошибки отправки (`except Exception`, не
   только rate-limit) — тоже ставить в очередь с тем же `DEFAULT_RETRY_SECONDS`,
   т.к. сетевой сбой тоже может быть временным.

**Готово, когда:** тест — `send_message` кидает `InstagramRateLimitError`,
после обработки в `main.py` в таблице `pending_messages` появляется строка
с правильным `recipient_id`/`text`/`retry_at`.

## Задача 3. Фоновый воркер, который досылает

**Проблема:** очередь сама по себе ничего не делает, нужен процесс, который
её разгребает.

**Действия:**
1. В `lifespan` (`src/main.py:55`, там же, где сейчас фоновые потоки
   `_load_faq`/`_load_tours`) добавить асинхронную фоновую задачу
   (`asyncio.create_task`, не `threading.Thread` — это async-код):
   ```python
   async def _pending_messages_worker():
       while True:
           await asyncio.sleep(30)  # период — обсудить, 30 сек разумный старт
           due = await get_due_pending(datetime.now(timezone.utc).isoformat())
           for row in due:
               lock = await _get_lock(row["recipient_id"])
               async with lock:
                   try:
                       await instagram.send_message(row["recipient_id"], row["text"])
                       await delete_pending(row["id"])
                       # здесь же — дописать сообщение в историю сессии,
                       # т.к. раньше (Задача 4) это отложено до реальной доставки
                   except InstagramRateLimitError as exc:
                       await _reschedule_or_giveup(row, exc.retry_after_seconds)
                   except Exception as exc:
                       await _reschedule_or_giveup(row, None)
   ```
2. `_reschedule_or_giveup`: если `attempts < MAX_ATTEMPTS` (константа,
   предлагается 5) — `mark_pending_retry` с новым `retry_at` и
   `attempts += 1`; иначе — `delete_pending` + `logger.error(
   "instagram.message.giveup", recipient_id=..., attempts=...)` +
   (см. Задачу 5) эскалация в Telegram.
3. **Обязательно** брать `_get_lock(recipient_id)` при досылке — иначе гонка
   с обычной обработкой нового сообщения от того же клиента, если оно
   приходит ровно в момент повторной отправки.
4. Задачу нужно хранить так же, как остальные фоновые таски
   (`_background_tasks`, `src/main.py:30`), чтобы не была garbage-collected.

**Готово, когда:** тест — в таблице лежит due-сообщение, воркер вызван один
раз вручную (без реального `asyncio.sleep`, замокать таймер/вызвать функцию
напрямую), после вызова `send_message` (замокан на успех) строка удалена
из очереди.

## Задача 4. Не сохранять в историю ответ, который не доставлен

**Проблема:** описана в разделе "Контекст" — `save_session` (`main.py:337`)
сейчас происходит до отправки, из-за чего история сессии врёт о том, что
клиент получил ответ, которого не было.

**Действия:**
1. В `process_with_ai` — переставить порядок: сначала пробовать
   `send_message` для всех chunks, и только **после успеха** (всех chunks)
   добавлять `{"role": "assistant", "content": clean_reply}` в историю и
   сохранять сессию.
2. Если отправка не удалась (ушла в очередь, Задача 2) — сессию всё равно
   нужно сохранить (обновить `last_message_at`, `escalation_count` и
   пользовательскую реплику `{"role": "user", ...}`), но **без** реплики
   ассистента — она допишется в историю фоновым воркером (Задача 3) в
   момент реальной успешной досылки.
3. Аналогично проверить `_process_non_text_safely` (`main.py:454-458`) — та
   же проблема: `client_reply` попадает в историю до отправки.

**Готово, когда:** тест — `send_message` падает, история сессии после
`process_with_ai` содержит реплику клиента, но НЕ содержит реплику
ассистента; после успешной досылки фоновым воркером — реплика ассистента
появляется в истории.

## Задача 5. Эскалация в Telegram при исчерпании попыток

**Проблема:** если сообщение так и не удалось доставить после
`MAX_ATTEMPTS` попыток — клиент навсегда останется без ответа, если никто
не заметит лог `instagram.message.giveup`.

**Действия:**
1. В `_reschedule_or_giveup` (Задача 3, п.2) при исчерпании попыток —
   вызвать `TelegramNotifier.notify_manager(...)` (уже используется в
   `main.py` для эскалаций, см. `src/services/telegram_notify.py`) с текстом
   вида "Не удалось доставить сообщение клиенту {recipient_id} после
   {MAX_ATTEMPTS} попыток — Instagram API недоступен/лимит. Ответьте
   вручную.".
2. Не путать с обычной эскалацией по `===МЕНЕДЖЕР===` — это отдельный,
   технический повод, стоит различать `tag` в уведомлении (например,
   `tag="Сбой доставки"`).

**Готово, когда:** тест — `attempts` достиг `MAX_ATTEMPTS`,
`TelegramNotifier.notify_manager` вызван один раз с соответствующим `tag`.

## Принципы

- Не превращать это в очередь произвольных задач общего назначения — это
  специализированное решение конкретно для недоставленных Instagram-сообщений,
  не нужно проектировать под гипотетические будущие типы задач.
- Фоновый воркер не должен держать `_get_lock` дольше, чем нужно на одну
  попытку отправки — не блокировать обработку новых сообщений того же
  клиента на всё время `asyncio.sleep`.
- Каждая задача — отдельный коммит.

## Открытые вопросы (решить перед стартом реализации)

1. **`DEFAULT_RETRY_SECONDS`** (если Meta не прислала `retry_after_seconds`) —
   предложено 60, можно другое.
2. **`MAX_ATTEMPTS`** — предложено 5, с растущим интервалом между попытками
   (например ×2 каждый раз) или фиксированным — обсудить.
3. **Период опроса воркера** — предложено 30 сек, зависит от того, насколько
   быстро хочется восстанавливать доставку после снятия лимита.
4. **Проактивная пауза при высоком `call_count`** (Задача 1, п.3) — делать
   сразу или сначала только логировать и решить по факту, если проблема
   окажется реальной, а не гипотетической.
5. Отдельная таблица в `data/sessions.db` или отдельный файл БД —
   технически проще в той же БД, но стоит подтвердить, что не будет
   конфликтов блокировок SQLite при одновременной записи из основного
   потока обработки и фонового воркера (SQLite поддерживает это, но нужно
   использовать одно и то же соединение/пул аккуратно, как уже сделано в
   `src/db/sessions.py`).
